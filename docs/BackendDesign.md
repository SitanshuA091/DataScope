# Endpoiints in API
## Auth
* `POST /auth/register` — creates a user account.
* `POST /auth/login` — verifies credentials and returns access/refresh tokens.
* `POST /auth/refresh` — issues a new short-lived access token.
* `POST /auth/logout` — invalidates the current refresh session/token.
* `GET /auth/me` — returns the signed-in user profile.

## Workspaces
* `POST /workspaces` — creates an empty workspace, optionally with a title.
* `GET /workspaces` — lists the user’s previous dataset workspaces.
* `GET /workspaces/{workspace_id}` — returns workspace details, dataset overview, recent runs, and chat history.
* `PATCH /workspaces/{workspace_id}` — renames a workspace.
* `DELETE /workspaces/{workspace_id}` — deletes the workspace, its dataset versions, results, and artifacts.

## Dataset upload and versions
* `POST /workspaces/{workspace_id}/datasets` — uploads and validates a CSV, creates a dataset/version, and returns lightweight schema information.
* `GET /datasets/{dataset_id}/overview` — returns row count, column count, column names, inferred types, and validation status.
* `GET /workspaces/{workspace_id}/datasets` — lists dataset versions within that workspace.
* `DELETE /datasets/{dataset_id}` — removes a selected dataset version and its derived artifacts.

For a first upload, the frontend can create the workspace and then call the upload endpoint. A corrected CSV uploaded to the same workspace becomes a new dataset version.

## Agent analysis and EDA runs
Use one generic endpoint—not separate public endpoints for high-level EDA, column EDA, and so on.

* `POST /datasets/{dataset_id}/analysis-runs` — accepts the user request and optional selected columns; creates a queued job for the agent to choose and execute valid EDA tools.
* `GET /analysis-runs/{run_id}` — returns status, progress stage, selected tools, final explanation, and failure details.
* `GET /datasets/{dataset_id}/analysis-runs` — lists prior analyses for the dataset, newest first.
* `POST /analysis-runs/{run_id}/retry` — creates/requeues a retry for a failed transient run.
* `POST /analysis-runs/{run_id}/cancel` — requests cancellation of a queued or running analysis.
* `GET /analysis-runs/{run_id}/results` — returns structured metrics, tool outputs, interpretation, and artifact references.
* `GET /analysis-runs/{run_id}/artifacts` — lists plot/table exports generated by that run.

Example request body:

```json
{
  "request": "Check data quality and investigate whether income relates to spending.",
  "selected_columns": ["income", "spending"]
}
```

The Celery worker then runs: agent planning → validated tool calls → EDA computation → plot generation → LLM interpretation → saved result.

## Dataset chat
* `POST /datasets/{dataset_id}/messages` — submits a dataset question and creates a chat/analysis run when computation is needed.
* `GET /datasets/{dataset_id}/messages` — loads persistent conversation history for that dataset session.
* `GET /datasets/{dataset_id}/question-usage` — returns the remaining question allowance if you enforce a per-session limit.

For questions such as “compare that with salary,” the API loads relevant prior run metadata and structured results, then lets the agent request the necessary new tool call. It should not send the whole raw dataframe directly to the LLM.

## Real-time updates
* `WS /ws/workspaces/{workspace_id}` — pushes events for upload validation, queued/running analysis jobs, progress stages, completion, and failure.

Example events:

```json
{ "type": "analysis.progress", "run_id": "…", "stage": "generating correlation heatmap" }
{ "type": "analysis.completed", "run_id": "…" }
```

On reconnect, the frontend calls `GET /analysis-runs/{run_id}` or `GET /workspaces/{workspace_id}` to recover the authoritative DB state.

## Operational endpoints
* `GET /health` — confirms the API is alive.
* `GET /ready` — checks required dependencies such as Postgres and Redis before accepting traffic.

Redis/Celery/cache do not need user-facing API endpoints. They stay internal: FastAPI creates the run and queues it; the worker executes it; Postgres records it; WebSockets notify the UI.
